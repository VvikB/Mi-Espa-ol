# Продолжение восстановления

Этот план не объявляет исторические проходы №1–11 выполненными и не заменяет MASTER SPECIFICATION.

1. **Довести G0 по всем кандидатам.** Получить ALL_AVAILABLE_HTML ZIP частями или через Git;
   проверить хэши и состав. Особое внимание: `Mi_Espanol_4_4_REBUILT_iPhone.html`,
   `Mi_Espanol_Integrated_Review_2026-11-02.html`, `Mi_Espanol_Personal_Complete_Review.html`,
   оригинальные Stage10/11, `mi_build/` и исторические тесты. Имена не являются доказательством версии.
2. **Сравнить содержимое, не только числа.** Для каждой архитектурной ветки снять DB/иные массивы,
   отдельные словари, упражнения, таблицы, картинки, сцены, планы, тексты и диалоги. Сохранить
   уникальные элементы по содержимому/источнику. Составить added/changed/missing и сверить
   исторические SHA-256. Только затем выбрать базу. LAST сейчас — предварительный кандидат
   по добавленным механизмам, а не по размеру файла; критические дефекты исключают приёмку.
3. **Подготовить устойчивую модель и миграцию.** Не менять оригинальные HTML. В отдельном
   модульном рабочем коде сопоставить `(source SHA, namespace, legacy index, content hash)` с
   будущим стабильным ID. Сохранить раздельные `state.vocab`, `state.answers`, `miRecall11`,
   настройки темы и recovery11-settings. Не переносить значения между несовпадающими словами
   по одному лишь индексу. Неизвестные поля/исходную копию сохранять. До миграции требуются
   реальные старые резервные копии, если они имеются.
4. **Отдельный обратимый пакет исправлений существующего поведения.** Сначала D01/D02:
   отказаться от строковых inline обработчиков с интерполяцией данных; делегирование событий,
   все испанские строки включая кавычки/ñ/пунктуацию; повторные UI-тесты словаря, карточек,
   таблиц и сцен. Затем D03/D04: связи недель и исходных страниц по реальному содержимому.
   Сопоставление восьми схем с семью страницами нельзя выдумывать по порядку массива.
5. **Надёжность.** D05–D08: строгая схема backup, атомарное восстановление, общий envelope
   настроек, merge с временем/источником и сохранением конфликтов; старый импорт не откатывает
   новые успехи. Обе очереди тестировать с фиксированным временем и сначала обслуживать due.
   Проверить v1/v2 и неизвестные будущие форматы, повторный импорт, повреждение/переполнение.
6. **G1/G2 — полнота и предметная проверка.** Получить первичные PDF/фото/книги; отдельно
   составить построчные матрицы для 16+7+2. Отмечать нечитаемое, происхождение и статус
   каждого элемента, не заменять отсутствующее новым авторским содержанием. Уровневая
   и методическая экспертиза A1–B2 — отдельная работа.
7. **G3/G4/G5.** Восстановить найденные уникальные функции и подтвердить весь курс по ID.
   Только затем рассматривать авторские дополнения. Сохранённый experimental draft требует
   собственного ревью и не интегрируется автоматически. Для каждой крупной интеграции:
   отдельный Git-коммит, counts/diff по исходному snapshot, текущие тесты, возможность отката.
8. **G6.** Выпуск после устранения критических дефектов, доказательства сохранности контента,
   сквозного QA и выделенной приёмки Safari iPhone. Никакой фиктивной оценки B2 или обещаний
   уникальности на рынке без соответствующей проверки.

Полезная работа, уже завершённая без ожидания файлов: консервация, текущий инвентарь,
сравнение двух кандидатов, тесты, список дефектов, реестр требований и способ передачи.
Окончательный выбор лучшей архитектуры требует недоставленных кандидатов; повторно
просить подтверждение самого аудита или начинать проект с нуля не требуется.
